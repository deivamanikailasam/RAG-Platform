## The big idea

> **ANALOGY · THE HOSPITAL MONITOR AND THE ON-CALL NURSE**
> A patient's bedside monitor records heart rate, oxygen and blood pressure every few seconds. That's
> Prometheus: numbers over time.
>
> The big screen at the nurses' station shows all patients at a glance. That's Grafana.
>
> The monitor doesn't page a doctor because one reading wobbled. It alarms when a reading stays outside a
> target range for long enough. That's an alert rule with a threshold and a duration.
>
> The on-call system decides who gets the page, groups ten alarms from one patient into one call, and stays
> quiet about minor issues while a critical one is being handled. That's Alertmanager.
>
> The hospital's promise, "95% of emergency patients seen within 30 minutes", is an SLO. The staff watch how
> fast they're using up the 5% slack, not every single wait.

## Why we're doing this

> **WHY THIS MATTERS**
> Traces explain one request; metrics explain the system. Questions like "Are searches getting slower this
> week?", "How often does the policy deny people?" or "Is the embedder saturated?" need numbers over time.
>
> Alerts are where operations succeeds or fails:
>
> - Too many and people mute them.
> - Too few and users find problems first.
> - Badly designed, they wake people at 3 a.m. for a blip that fixed itself.
>
> SLO-based alerting is the industry answer: define what "good enough" means for users, and alert only when
> you're on track to break that promise.

| Need | How this step meets it |
|---|---|
| Store and query metrics | Prometheus time-series database + PromQL |
| Our services and off-the-shelf ones together | OTLP push (via the Collector) + scrape (`/metrics`) |
| "Is search good enough?" | SLO: 99% succeed, 95% under 2 s; error budget |
| Alerts that mean something | Burn-rate alerts over two windows; `for` durations; severities |
| The right person, once | Alertmanager: group, de-duplicate, route, inhibit, silence |
| Alerts that are correct | Unit tests for every rule (`promtool test rules`) |
| Readable, reviewable dashboards | Provisioning + dashboards as code (generated JSON, drift check) |
| What to do when it fires | A runbook link on every alert |

> **IN A COMPANY**
> SLOs are how engineering and the business agree on reliability:
>
> - "99% of searches succeed over 28 days" is specific, measurable and testable.
> - The error budget (the remaining 1%) becomes a decision tool. Budget left? Ship features. Budget burning?
>   Prioritise reliability.
> - SLAs are contractual promises to customers, set looser than internal SLOs so you get warned before you owe
>   refunds.
>
> Expect to be asked for SLO definitions, alert runbooks and evidence that alerts are tested.

## Key ideas

| Term | Plain-English meaning |
|---|---|
| Time series | One metric with one set of labels, sampled over time, e.g. `rag_search_requests_total{outcome="ok"}`. |
| Scrape (pull) vs push | Prometheus fetches `/metrics` from a target, or the Collector sends metrics to Prometheus (OTLP). |
| Exporter | A small adapter that turns a system's statistics (e.g. Postgres) into `/metrics`. |
| PromQL | Prometheus's query language. |
| `rate()` / `increase()` | Per-second speed / total growth of a counter over a window, handling restarts. |
| Histogram and buckets | Counts of values below fixed edges ("≤ 0.5 s", "≤ 1 s"…); `histogram_quantile` estimates p95 from them. |
| Recording rule | A query Prometheus pre-computes and stores under a new name, to keep dashboards and alerts fast. |
| Alert rule / `for` | A condition that must stay true for a duration before the alert fires. |
| SLI / SLO / SLA | Indicator (what you measure) / Objective (your target) / Agreement (the contract with customers). |
| Error budget | The allowed failure: with a 99% SLO, 1% of searches may fail per period. |
| Burn rate | How fast the budget is being used. 1× uses it exactly in the period; 14.4× uses a 28-day budget in ~2 days. |
| Grouping / inhibition / silence | Several alerts become one message / a critical alert mutes its warning twin / mute on purpose during maintenance. |
| Runbook | Step-by-step instructions linked from an alert: what it means, what to check, how to fix. |

> **IN PLAIN ENGLISH · LABELS AND TIME SERIES**
> A metric name says *what* is counted (`rag_search_requests_total`); labels say *which slice*
> (`outcome="ok"` or `outcome="error"`, `job="rag-api"`, `service_version="0.1.0"`). Every distinct combination of
> labels is its own time series. That's why labels must have few possible values: a label holding a user id or a
> query text would create one series per user or per question, and Prometheus would run out of memory
> ("high cardinality").

> **IN PLAIN ENGLISH · COUNTERS, `rate()` AND `increase()`**
> A counter only ever goes up (searches served so far). Its raw value is not interesting; how fast it grows is.
> `rate(x[5m])` is "per second, averaged over the last 5 minutes"; `increase(x[15m])` is "how much it grew in the
> last 15 minutes". Both understand that a counter falling back to 0 means the process restarted, not that the
> world reversed.

> **IN PLAIN ENGLISH · HISTOGRAMS AND p95**
> A histogram doesn't keep every search time. It keeps a few counters: how many searches took ≤ 0.025 s,
> ≤ 0.05 s, … ≤ 2 s, ≤ 3 s and so on (the bucket edges). `histogram_quantile(0.95, …)` finds the bucket where
> the 95th percentile falls and estimates a value inside it. So the edges decide how precise p95 can be, which
> is why the bug in section 9 mattered.

### Error budgets and burn rates

```text
 ERROR BUDGET LEFT (objective 99% → budget = 1% of searches may fail in 28 days)
 100% ┤╲╲─────────────────────────────────────────────── 1× burn: on track, lasts exactly 28 days
      │ ╲ ╲──────────
  50% ┤  ╲    ╲────────╲──────────                        6× burn: gone in ~5 days → ticket
      │   ╲            ╲
   0% ┤    ╲(~2 days)   ╲(~5 days)                        14.4× burn: gone in ~2 days → page
      └───────────┬───────────┬───────────┬───────────┬──
           day 0        day 7      day 14     day 21    day 28

 Alert on how FAST the budget burns (two windows each: 1h+5m for pages, 6h+30m for tickets), not on single errors.
```

*Figure 64. Burning the error budget. At 1× the budget lasts the full 28 days; at 6× it's gone in about 5 days
(open a ticket); at 14.4× in about 2 days (page someone). Alerting on burn rate ignores harmless blips and
catches real trends.*

Where the numbers come from: a 99% objective allows 1% failures. A burn rate of 14.4 means failing at
14.4 × 1% = 14.4% of searches; at that pace a 28-day budget lasts 28 / 14.4 ≈ 1.9 days. A burn rate of 6 means
6% failing, and the budget lasts 28 / 6 ≈ 4.7 days.

> **WHY TWO WINDOWS PER ALERT**
> The fast-burn page needs both:
>
> - the last hour burning at 14.4×, so it's a real trend, not a 2-minute blip
> - the last 5 minutes too, so the alert stops quickly once things recover
>
> The slow-burn ticket uses 6 hours and 30 minutes the same way. This pattern (from Google's SRE Workbook) is
> the standard way to alert on SLOs. The unit tests below prove that a 4-minute blip does not page while a
> sustained 30% failure does.

### 3 · Prometheus

File: `infra/config/prometheus/prometheus.yml`

```yaml
# Prometheus: stores the platform's metrics, evaluates alert rules, hands firing alerts to Alertmanager.
global:
  scrape_interval: 15s                        # how often to pull from each target
  evaluation_interval: 15s                    # how often to evaluate rules
  external_labels:
    environment: dev                          # added to every alert, so receivers know where it came from

# Metrics PUSHED by the OpenTelemetry Collector (our own services) arrive on /api/v1/otlp.
otlp:
  promote_resource_attributes:                # copy these resource facts onto every series as labels
    - service.version
    - deployment.environment.name

rule_files:
  - /etc/prometheus/rules/*.yml

alerting:
  alertmanagers:
    - static_configs:
        - targets: ["alertmanager:9093"]

# Metrics PULLED ("scraped") from components that expose /metrics themselves.
scrape_configs:
  - job_name: prometheus
    static_configs: [{ targets: ["localhost:9090"] }]
  - job_name: alertmanager
    static_configs: [{ targets: ["alertmanager:9093"] }]
  - job_name: otel-collector                  # the Collector's own health
    static_configs: [{ targets: ["otel-collector:8888"] }]
  - job_name: keycloak                        # sign-ins, failures, JVM, DB pool (management port)
    static_configs: [{ targets: ["keycloak:9000"] }]
  - job_name: opa                             # decision latency, bundle status
    authorization:
      credentials_file: /run/secrets/opa_metrics_token   # system.authz only lets this token read /metrics
    static_configs: [{ targets: ["opa:8181"] }]
  - job_name: qdrant
    authorization:
      credentials_file: /run/secrets/qdrant_read_only_api_key
    static_configs: [{ targets: ["qdrant:6333"] }]
  - job_name: postgres-rag                    # via postgres_exporter, logged in as the read-only rag_metrics role
    static_configs: [{ targets: ["postgres-exporter:9187"] }]
  - job_name: tei                             # embedder + reranker run natively on macOS (Step 8)
    static_configs: [{ targets: ["host.docker.internal:9083", "host.docker.internal:9084"] }]
```

> **READING THE SCRAPE JOBS**
>
> - `otlp.promote_resource_attributes`: resource facts like `service.version` become labels, so you can compare
>   versions on a dashboard. Without this, they live only in a separate `target_info` series.
> - `authorization.credentials_file`: Prometheus sends a bearer token read from a secret file.
>   - OPA gets a metrics-only token: the policy update below lets it read `/metrics` and nothing else.
>   - Qdrant gets its read-only key.
> - `host.docker.internal`: how a container reaches services running natively on your Mac, here the TEI embedder
>   and reranker (Step 8) with their metrics ports.
> - `external_labels`: every alert carries `environment=dev`, so a shared Alertmanager can tell dev from
>   production.

### 4 · The search SLO and its alerts

File: `infra/config/prometheus/rules/slo-rag-search.yml`

```yaml
# Service level objective (SLO) for search: 99% of searches succeed, measured over 28 days.
# Error budget = the 1% that may fail. Alerts fire on how FAST the budget is being spent ("burn rate").
groups:
  - name: rag-search-slo-recordings
    rules:
      # Fraction of searches that failed, over several windows (recording rules = precomputed queries).
      - record: rag:search_errors:ratio_rate5m
        expr: |
          sum(rate(rag_search_requests_total{outcome="error"}[5m]))
          / sum(rate(rag_search_requests_total[5m]))
      # … the same for 30m, 1h and 6h …
      - record: rag:search_latency:p95_5m
        expr: histogram_quantile(0.95, sum by (le) (rate(rag_search_duration_seconds_bucket[5m])))

  - name: rag-search-slo-alerts
    rules:
      # Fast burn: at this rate the whole 28-day budget is gone in ~2 days. Wake someone up.
      - alert: RagSearchErrorBudgetFastBurn
        expr: |
          rag:search_errors:ratio_rate1h > (14.4 * 0.01)
          and rag:search_errors:ratio_rate5m > (14.4 * 0.01)
        for: 2m
        labels: { severity: critical, service: rag-api }
        annotations:
          summary: "Search is failing fast: {{ $value | humanizePercentage }} of searches in the last 5 min"
          runbook: docs/runbooks/rag-search-errors.md
      # Slow burn: budget gone in ~5 days. A ticket for working hours, not a page.
      - alert: RagSearchErrorBudgetSlowBurn
        expr: |
          rag:search_errors:ratio_rate6h > (6 * 0.01)
          and rag:search_errors:ratio_rate30m > (6 * 0.01)
        for: 15m
        labels: { severity: warning, service: rag-api }
        # summary + runbook…
      # Latency objective: 95% of searches under 2 seconds.
      - alert: RagSearchSlow
        expr: rag:search_latency:p95_5m > 2
        for: 10m
        labels: { severity: warning, service: rag-api }
        # summary + runbook docs/runbooks/rag-search-latency.md
```

File: `infra/config/prometheus/rules/security.yml`

- **`RagPolicyQueryMismatch`** (critical): `increase(rag_search_dropped_documents_total[15m]) > 0`. The
  post-check dropped a document the query returned: the SQL filter and the policy disagree. Nothing leaked (the
  post-check worked), but something is wrong. Always investigate. No `for`: it fires immediately.
- **`KeycloakLoginFailuresHigh`** (warning): more than 20 failed sign-ins in a realm in 10 minutes
  (`keycloak_user_events_total{event="login", error!=""}`): password guessing, or a broken client. Lockout
  (Step 16) limits the damage.

File: `infra/config/prometheus/rules/platform.yml`

- **`TargetDown`** (warning): `up == 0` for 2 minutes.
- **`OtelCollectorLosingData`** (warning): the Collector is refusing data (memory limit hit) or failing to deliver
  it for 5 minutes. Its expression adds six explicitly named counters (`otelcol_receiver_refused_spans`,
  `…_metric_points`, `…_log_records`, `otelcol_exporter_send_failed_spans`, …), each with `or vector(0)`.

> **IN PLAIN ENGLISH · WHY `or vector(0)`**
> If one of the six counters doesn't exist yet (no logs have been sent, say), `sum(rate(that[5m]))` returns
> *nothing*, and "nothing + a number" is also nothing in PromQL, so the whole alert could never fire.
> `or vector(0)` says "if there's nothing, use 0", so the other five terms still count.

> **CHOOSING SEVERITIES**
>
> - **critical** (page a human now): users are being hurt or a security control misfired. That's the fast
>   error-budget burn, or the policy/query mismatch.
> - **warning** (ticket, working hours): the slow burn, latency over objective, a target down, telemetry loss.
>
> Every alert has a runbook link and a summary written for a tired person at 3 a.m.: what is wrong, with the
> number.

### 5 · Test the alerts like code

`promtool` feeds fake time series into the rules and checks which alerts fire, when, and with which text. These
tests are the proof that the alerting does what you think it does.

File: `infra/config/prometheus/tests/rules_test.yml` holds seven test groups:

| # | Fake data | Expected |
|---:|---|---|
| 1 | 1% errors for 2 hours (inside the budget) | no fast-burn and no slow-burn alert |
| 2 | 30% of searches fail for 90 minutes | at 75 min, `RagSearchErrorBudgetFastBurn` (critical) with summary "Search is failing fast: 30% of searches in the last 5 min" |
| 3 | an hour of health, then a 4-minute blip at 30% failures, then health | at 66 min, **no** page: the 1-hour window stays under 14.4% |
| 4 | every search takes ~3 s (lands in the `le="5"` bucket) | at 18 min, `RagSearchSlow` with "p95 search latency is 4.875s (objective: under 2s)" |
| 5 | `rag_search_dropped_documents_total` goes 0 → 1 | at 4 min, `RagPolicyQueryMismatch`: "Search returned 1 document(s) the policy then refused" |
| 6 | `up{job="opa"}` goes 1, 1, 0, 0, 0, 0 | nothing at 3 min (only 1 minute down); `TargetDown` at 5 min |
| 7 | `otelcol_receiver_refused_spans` grows by 50 a minute | at 8 min, `OtelCollectorLosingData` |

> **READING A TEST CASE**
>
> - `values: "0+70x90"` means start at 0 and add 70 every interval, 90 times: a counter growing by 70 a minute.
> - `exp_alerts: []` asserts that nothing fires.
> - Test 3 is the important one: a real 4-minute failure does not page, because the 1-hour window stays under the
>   threshold. That's the burn-rate design working.

### 6 · Alertmanager

File: `infra/config/alertmanager/alertmanager.yml`

```yaml
# Alertmanager: groups, de-duplicates, silences and routes alerts to people.
route:
  receiver: platform-team                     # default destination
  group_by: [alertname, service]              # one notification per problem, not one per series
  group_wait: 30s                             # wait briefly to batch related alerts
  group_interval: 5m
  repeat_interval: 4h                         # remind, but don't spam
  routes:
    - matchers: ['severity="critical"']
      receiver: platform-team-urgent
      repeat_interval: 1h

inhibit_rules:                                # while a critical alert fires, mute its warning twin
  - source_matchers: ['severity="critical"']
    target_matchers: ['severity="warning"']
    equal: [alertname, service]

receivers:
  # Locally, alerts are visible in the Alertmanager UI and in Grafana. In a company you'd add e.g.:
  #   slack_configs: [{ api_url_file: /run/secrets/slack_webhook_url, channel: "#rag-alerts" }]
  #   email_configs: [{ to: platform-team@example.com, ... }]
  #   pagerduty_configs: [{ routing_key_file: /run/secrets/pagerduty_key }]     (urgent only)
  - name: platform-team
  - name: platform-team-urgent
```

> **IN PLAIN ENGLISH · GROUPING, INHIBITION, SILENCES**
>
> - **Grouping:** ten `TargetDown` alerts in the same 30 seconds become one notification listing ten targets.
> - **De-duplication:** Prometheus re-sends a firing alert every evaluation; Alertmanager notifies once and then
>   only every `repeat_interval`.
> - **Inhibition:** while a critical alert fires, a warning with the same `alertname` and `service` is muted, so
>   the person paged isn't also flooded with its lesser twin.
> - **Silence:** a deliberate, time-limited mute you create in the UI ("OPA maintenance, 30 minutes"). Silences
>   are stored in the `alertmanager-data` volume and survive restarts.

### 7 · Dashboards as code

Grafana dashboards are JSON documents of several hundred lines. Editing them by hand, or clicking and saving in
the UI, makes review impossible. Instead, a short Python script generates the JSON. You commit both, and
`just dashboards-check` fails if someone edits one without the other. (Libraries like the Grafana Foundation SDK
or Grafonnet do the same at larger scale.)

File: `scripts/build_dashboards.py`. A tiny `Dashboard` class with four helpers (`row`, `stat`, `series`,
`targets_table`) and one function per dashboard. `rag_overview()` builds *RAG platform · overview*:

| Row | Panels |

### 9 · The three bugs the live test found

This step was tested end to end before being written down:

- **Setup:** rag-api (with real OPA) → Collector → Prometheus via OTLP → rules → Alertmanager.
- **Traffic:** normal searches, a simulated query/policy mismatch, then OPA switched off.
- **Checks:** every dashboard query run against the live data.

The rules were valid and their unit tests passed, yet three real bugs only showed up with real data:

```text
 SDK default edges (meant for milliseconds), unit = seconds
   ≤0 │ ≤5 │ ≤10 │ ≤25 │ ≤50 │ ≤75 │ ≤100 │ ≤250 │ ≤500 │ ≤1000 …
   A 0.05 s search lands in "0–5 s". Prometheus assumes it could be anywhere in there → p95 ≈ 4.75 s. False alarm.

 Explicit edges in seconds (this step), with one AT the 2 s objective
   ≤0.025 │ ≤0.05 │ ≤0.1 │ ≤0.25 │ ≤0.5 │ ≤1 │ ≤2 │ ≤3 │ ≤5 │ ≤10 │ ≤30
   The same search lands in "0.025–0.05 s" → p95 ≈ 0.05 s. Correct, and "under 2 s?" is an exact bucket count.
```

*Figure 65. The histogram bucket pitfall. With the SDK's default bucket edges (meant for milliseconds) every
fast search falls into the 0–5 s bucket, and p95 is estimated at about 4.75 s: a false latency alarm. Explicit
edges in seconds, with one at the 2 s objective, give the right answer.*

1. **Histogram buckets in the wrong unit.** OpenTelemetry's default edges (0, 5, 10, 25 … 10 000) assume
   milliseconds. Our durations are in seconds, so every 50 ms search landed in the "0–5" bucket, and
   `RagSearchSlow` started firing falsely at a reported p95 of ~4.75 s.
   *Fix:* explicit bucket edges in seconds, one exactly at the 2 s objective. A new test
   (`test_latency_buckets_are_in_seconds`) guards it.
2. **Counters born mid-incident.** A counter only exists after its first `add()`. So the very first dropped
   document creates `rag_search_dropped_documents_total` at 1. `increase()` can't see a jump from "no data" to 1,
   so the security alert could miss the first event.
   *Fix:* add 0 to alert-worthy counters at start-up.
3. **The Collector's metric names and a query error.** The Collector's own counters have no `_total` suffix in
   this version, so a rule written by the book matched nothing and could never fire. Matching several of them with
   one name pattern then made Prometheus reject the query (HTTP 422) once more than one existed.
   *Fix:* explicit names, each with `or vector(0)`. Unit test 7 covers it.

Bugs 1 and 2 are fixed in rag-api. `services/rag-api/src/rag_api/main.py`:

```python
# Bucket edges in SECONDS. The SDK's defaults (0, 5, 10, 25 … 10000) assume milliseconds: with them,
# every search lands in the 0-5 bucket and p95 is reported as ~4.75 s. Put an edge at the 2 s objective.
SEARCH_BUCKETS = [0.025, 0.05, 0.1, 0.25, 0.5, 1, 2, 3, 5, 10, 30]
SEARCH_TIME = meter.create_histogram(
    "rag.search.duration",
    unit="s",
    description="End-to-end search time",
    explicit_bucket_boundaries_advisory=SEARCH_BUCKETS,
)

# in lifespan(), after the instrumentors:
    # Start alert-worthy counters at 0. Otherwise a counter is born at its first value, and
    # Prometheus' increase() can't see the jump from "nothing" to 1: the first incident is missed.
    for outcome in ("ok", "error"):
        SEARCHES.add(0, {"outcome": outcome})
    DROPPED.add(0)
```

`libs/rag-common/src/rag_common/telemetry.py` honours the standard interval setting:

```python
    # How often metrics are sent: standard OTEL_METRIC_EXPORT_INTERVAL (ms); we default to 15 s.
    interval_ms = int(os.getenv("OTEL_METRIC_EXPORT_INTERVAL", "15000"))
    reader = metric_reader or PeriodicExportingMetricReader(
        OTLPMetricExporter(), export_interval_millis=interval_ms
    )
```

And `services/rag-api/tests/test_telemetry.py` adds `test_latency_buckets_are_in_seconds`: the
`rag.search.duration` histogram must have an edge at exactly 2 and a first edge below 0.1.

> **THE LESSON**
> Config validation and unit tests prove your rules are well-formed and logically right. Only real data through
> the real pipeline proves the names, units and shapes match. Do both, every time you add a metric or an alert.

## Benefits

- **One place for all numbers:** our services and every off-the-shelf component.
- **User-centred alerting:** SLOs and burn rates page only when users are really affected.
- **Tested alerts:** each rule proven with fake data before it ever fires for real.
- **Fewer, better notifications:** grouping, inhibition, severity routing and runbooks.
- **Reviewable dashboards:** generated from code, drift-checked, never lost to a stray click.
- **Least privilege throughout:** a metrics-only OPA token, a read-only Qdrant key, a `pg_monitor` database role.
- **Real bugs caught early:** units, counter start values and metric names, found by the live test.

## Drawbacks and risks

- **No built-in auth on Prometheus and Alertmanager:** keep them private, and put a proxy in front in production.
- **Single node:** if Prometheus is down, no alerts fire. Production runs an HA pair and clustered Alertmanagers,
  plus a "dead man's switch" alert that should always fire (so its *absence* tells you alerting is broken).
- **Local retention only (15 days);** long-term storage needs Mimir, Thanos or a managed service.
- **Metric names can change** with Collector or library upgrades; the live test and `TargetDown` help catch it.
- **SLO targets are guesses at first:** review them with real traffic and users (Step 37).

## Alternatives

| Option | What it is, in plain words | Choose it when |
|---|---|---|
| Prometheus + Alertmanager + Grafana (our choice) | The open-source standard stack | Self-hosted, Kubernetes-friendly, huge ecosystem |
| VictoriaMetrics | Prometheus-compatible, very efficient storage | Large volumes on modest hardware |
| Grafana Mimir / Thanos | Scale-out, long-term Prometheus storage | Many clusters, months or years of retention |

## Which approach fits which situation

| Situation | Best choice |
|---|---|
| Local platform | Single Prometheus + Alertmanager + Grafana (this step) |
| Production, one cluster | Prometheus HA pair (or the Prometheus Operator), Alertmanager cluster, auth proxy |
| Many clusters, long retention | Mimir or Thanos behind the same Grafana |
| Many teams, many SLOs | SLO generators (Sloth, Pyrra) + SLO dashboards per service |
| Regulated environment | Alert and SLO definitions reviewed like code; tested; access-controlled UIs |

## Common mistakes

- Alerting on causes ("CPU 80%") instead of symptoms users feel (errors, latency).
- Single-window or no-`for` alerts that page on every blip.
- Untested rules that never fire, like a metric name typo or a missing `_total`.
- High-cardinality labels (user ids, document ids, query text) on metrics.
- Default histogram buckets in the wrong unit, or no bucket at the objective.
- Counters that only appear on first use, so the first incident is invisible to `increase()`.
- Dashboards edited in the UI and lost, or never reviewed.
- Exposing Prometheus or Alertmanager without authentication.
- Alerts without runbooks: the person paged has to guess.
